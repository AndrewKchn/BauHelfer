# Spec: site language and the language switcher (#29)

Status: **agreed**. I decided D1–D4 on 2026-11-06 (my criteria: simple code and usability
first). D5–D14 are Claude's defaults, which I accepted on 2026-11-06, before any tests.

Marks: **(mine, date)** — my decision; **(Claude's default, accepted)** — Claude's default
that I accepted.

## Goal

Every UI string is already wrapped in `{% translate %}` / `gettext`, but Django has no
translations and no way to pick a language: everyone sees English. This ticket turns i18n on
for the 7 languages, adds a switcher to the header and stores a logged-in user's choice in
`User.preferred_language`, the field the emails (#27) already read. It also adds the checks
that keep the `.po` / `.mo` files complete and current.

Two iterations in one branch and one PR:

1. i18n on: settings, the switcher, the choice saved in the profile.
2. The translation checks: untranslated / fuzzy strings, `.mo` up to date; `gettext` in CI.

### Out of scope

- Translating the ~390 strings of M2–M4: #30 (D2).
- Translating user content (jobs, messages): #31–#34, #36.
- The language in the URL (D1).

## Iteration 1: i18n on, the switcher, the profile

### Requirements

R1. `config/settings/base.py`: `LANGUAGES` lists the 7 codes `de en ru uk pl ro tr` with the
    names of `User.Language` (each in its own language, D6); `LANGUAGE_CODE = "en"` (D5);
    `LOCALE_PATHS = [BASE_DIR / "locale"]`.
R2. `django.middleware.locale.LocaleMiddleware` in `MIDDLEWARE` after `SessionMiddleware` and
    before `CommonMiddleware` (where Django's docs put it). It picks the language from the
    `django_language` cookie, then the browser's `Accept-Language`, then `LANGUAGE_CODE`.
R3. `accounts.middleware.UserLanguageMiddleware`, after `AuthenticationMiddleware`: for a
    logged-in user it activates `user.preferred_language` and sets `request.LANGUAGE_CODE`,
    whatever the cookie says (D3). Guests are left to `LocaleMiddleware`.
R4. `POST /accounts/language/` (`set_language`, D8): takes `language` and `next`. Calls
    Django's `django.views.i18n.set_language`, which checks the code, sets the cookie and
    redirects to `next` only if it is on our site (otherwise to `/`). A logged-in user also
    gets `preferred_language` saved. An unknown code changes nothing. GET is refused (405).
R5. `OnboardingMiddleware.is_allowed` lets `set_language` through: a user without a role can
    switch the language on the role page.
R6. Signup stores the language active at that moment in `preferred_language` (D9).
R7. The header has the switcher on every page, for guests and logged-in users, left of the
    "Log in" / ☰ buttons (D7): a `<details>` drop-down whose button shows the current code
    in capitals ("EN"); the menu has one button per language with its own name, the current
    one marked (✓, `aria-current`). One form, `next` = the current page with its query
    string.
R8. `locale/<code>/LC_MESSAGES/django.po` for the 6 languages other than English (D10),
    made by `makemessages`, and the `.mo` files next to them (D4). The strings added in this
    ticket are translated into all 6.

### Acceptance criteria (→ tests)

AC1. `LANGUAGES` has exactly the 7 codes and the same names as `User.Language`.
AC2. `LocaleMiddleware` is between `SessionMiddleware` and `CommonMiddleware`;
     `UserLanguageMiddleware` is after `AuthenticationMiddleware`.
AC3. A guest who switches to `ru` gets the `django_language=ru` cookie, is redirected to
     `next`, and the next page has `<html lang="ru">` and a Russian string from this ticket.
AC4. A guest without a cookie whose browser sends `Accept-Language: pl` gets Polish; one
     whose browser sends a language we do not have gets English.
AC5. A logged-in user who switches to `uk` has `preferred_language == "uk"` in the database.
AC6. A logged-in user with `preferred_language = "ru"` and the cookie `de` gets Russian (D3).
AC7. An unknown code (`xx`) changes neither the cookie nor the database; `next` pointing to
     another site redirects to `/`; GET gets 405.
AC8. A user without a role can switch the language and is not sent to the role page by it.
AC9. A guest who switched to `ro` and signs up has `preferred_language == "ro"`.
AC10. The header has the switcher for a guest and a logged-in user: the current code, 7
      buttons, the current one marked.

## Iteration 2: the translation checks

### Requirements

R9. `tests/test_translations.py` runs `msgattrib --untranslated` and `msgattrib --only-fuzzy`
    (from `gettext`, D11) on every `.po` file in `locale/`; obsolete entries (`#~`) do not
    count.
R10. That check on our real `.po` files is marked `xfail(strict=True, reason="#30")` (D2):
     it is expected to fail until #30 translates the M2–M4 strings, and turns CI red as soon
     as it passes, so #30 has to remove the marker.
R11. Every `.mo` matches its `.po` (D4): the test compiles each `.po` to a temporary file with
     `msgfmt` and compares the two catalogs (all msgid → msgstr pairs, read with Python's
     `gettext` module), not the bytes: different `gettext` versions write different bytes
     (D12).
R12. CI installs `gettext` (`apt-get install gettext`) before the tests.
R13. `CLAUDE.md` → Commands: `sudo apt install gettext` (once per machine), `makemessages`
     and `compilemessages` with the flags we use.

### Acceptance criteria (→ tests)

AC11. A sample `.po` with one untranslated string is reported; one with a fuzzy string is
      reported; a fully translated one is not.
AC12. The check on `locale/` fails today (xfail) because of the M2–M4 strings.
AC13. A `.mo` compiled from a changed `.po` is reported as out of date; the committed ones are
      not.

## Decisions

D1. **The language is in a cookie, not in the URL** (mine, 2026-11-06; option A). A link
    opens in the reader's own language; no URL, test or `OnboardingMiddleware` path changes.
    Rejected: `i18n_patterns` (`/ru/jobs/5/`, B: a link can choose the language and search
    engines see every language, but ~15–20 path changes in code and tests). Costs: search
    engines see one language; one URL returns different HTML (fine without a shared cache);
    a new cookie `django_language` (necessary, set by the user's own choice, no consent
    needed; → `docs/SECURITY.md`). Changing to B later changes every URL. **Revisit when**
    search in several languages matters.
D2. **The untranslated/fuzzy check is a pytest test, `xfail(strict=True)` until #30** (mine,
    2026-11-06; option B). Rejected: translating all M2–M4 strings now (A: the PR grows
    many times, #30 would be empty); checking only new strings against `main` (C: a fragile
    git diff, useless after #30). Costs: until #30 nothing fails on a new untranslated
    string. The issue's "Done when" was changed to match (2026-11-06). **Revisit when** #30
    is done: it removes the marker.
D3. **For a logged-in user the profile wins over the cookie** (mine, 2026-11-06; option A):
    one source of truth, so the site and the emails are in the same language on every
    device. Rejected: reading the profile only at login and then the cookie (B: the two can
    differ until the next login). Costs: one more middleware whose place in the chain
    matters.
D4. **The `.mo` files are in git** (mine, 2026-11-06; option A): Render needs no `gettext`,
    as in Django's own repository; a test catches a `.mo` that is older than its `.po`
    (R11). Rejected: compiling on Render at build time (B: Render's Python environment has
    no root, and whether it has `msgfmt` is unknown until a deploy). **Revisit when**
    Render can compile them, or the `.mo` files conflict in merges.
D5. **The default language is English** (Claude's default, accepted): `LANGUAGE_CODE = "en"` (was
    `"en-us"`, which is not one of the 7). It is used when the browser asks for none of our
    languages. English, not German: the strings are written in English, so it is always
    complete, and the mockups show "EN".
D6. **Each language is named in its own language** ("Deutsch", "Русский") (Claude's
    default): a person who does not read the current language still finds their own. Not
    translated, so not in the `.po` files. The names come from `User.Language`; a test keeps
    `LANGUAGES` equal to it, since settings cannot import a model.
D7. **The switcher is its own button "EN" next to ☰, for everyone** (Claude's default, accepted), as
    on the mockup. Not inside the ☰ menu: guests have no menu, and a person who cannot read
    the page must find it at once.
D8. **Our own view around Django's `set_language`** (Claude's default, accepted): Django's view already
    checks the code, sets the cookie and refuses a `next` to another site; ours only adds
    saving the profile. Under `/accounts/language/`, so the name stays `set_language`, as in
    the issue.
D9. **Signup saves the current language** (Claude's default, accepted): otherwise a guest who chose
    Russian gets `en` in the profile and, by D3, sees English after the first login.
D10. **No `.po` for English** (Claude's default, accepted): the strings in the code are English; an
     English `.po` would only hold empty translations, and the check would always fail on
     it.
D11. **`msgattrib` + `subprocess`, no new dependency** (Claude's default, accepted): `polib` would be
     a new package for one test; `gettext` is needed anyway.
D12. **`.mo` compared by content, not by bytes** (Claude's default, accepted): my machine has
     `gettext` 0.23, CI 0.21; their `.mo` bytes may differ for the same `.po`.
D13. **After logout the page follows the cookie again** (Claude's default, accepted): a user who logs
     in on someone else's phone sees their language; after logout, that phone's. Not
     fixed: the person logging out is leaving.
D14. **Two iterations** (Claude's default, accepted): the switcher first, so the checks run on real
     `.po` files.

## Known limitations (→ docs/SECURITY.md)

- New cookie `django_language` (D1): the chosen language only, necessary, no consent.
- Until #30 the CI does not fail on untranslated strings (D2).
- A string added to the code without running `makemessages` is not in any `.po`, so no check
  sees it. **Revisit when** #30: a check that `makemessages` changes nothing.
